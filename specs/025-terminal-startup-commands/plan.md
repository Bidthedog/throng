# Implementation Plan: Terminal Startup Commands & Command Memory

**Branch**: `feature/S025-I12-terminal-startup-commands` | **Date**: 2026-07-27 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification — 3 user stories, 68 functional requirements, 15 success criteria, 9
clarifications resolved. Closes #12, #96, #113.

## Summary

Give each Terminal Panel a durable memory of what it was doing: a **Startup Command** it runs on cold
start, an **opt-in** rule that keeps that command up to date from whatever was actually running when the
terminal ended, and its **last working directory**. Rename the existing "Startup Params" to "Shell
Arguments" all the way down to the persisted keys, with a read-side migration.

The design leans on three things that already exist and were found by reading the code rather than
assumed: the pure `resolveLaunchSpec` seam that composes a launch, the daemon's batched 1-second poll
that already reports every terminal's live cwd, and the descendant-process query that already runs a
`Win32_Process` snapshot exposing `CommandLine`. See [research.md](./research.md).

## Technical Context

**Language**: TypeScript 5.9 (ceiling), ESM, npm workspaces
**Runtime**: Electron 40+ (UI main + renderer), Node daemon over a named pipe
**Testing**: vitest (`unit` / `integration` / `contract` projects), Playwright (E2E). No component-test
stack — renderer behaviour is proven by E2E, pure logic by unit tests in `@throng/core` (research R7).
**Platform**: Windows only (macOS/Linux are #22/#23)
**Constraints**: capture must not delay teardown (FR-024) and must not scale with terminal count
(FR-019a); the daemon is single-threaded, so nothing new may block its event loop (FR-019b).

No unresolved unknowns. Every question the spec deferred to planning is answered in research.md, and the
per-flavour recipes were **empirically proven**, not assumed (FR-013).

## Constitution Check

| Principle | Standing |
|---|---|
| **I. Project isolation** | A remembered command/directory lives on its Panel and is never shared. A remembered cwd outside the owning project falls back to the root (FR-030). ✔ |
| **II. Platform-abstracted core** | Command-line introspection enters through `IPtyHost.listChildProcesses`; all selection rules are pure (`command-capture.ts`, `command-recipe.ts`). No OS call outside `platform-windows`. ✔ |
| **III. Detached, tagged, persistent terminals** | This principle **requires** the feature: it mandates each terminal be tagged with "launch command/preset" and working directory, and that presets reconstitute a cold project. Delivers the two of five tags not yet honoured. Busy-terminal survival is respected — leaving a terminal running is explicitly *not* a capture point (FR-021). ✔ |
| **IV. Native terminal support** | Recipes are per flavour and declarable for user-defined flavours (FR-011), with a universal fallback (FR-012) — no flavour is privileged. **No new key binding is taken**, so the reserved/shadowable tiers are untouched. ✔ |
| **V. Test-first (NON-NEGOTIABLE)** | Every task is Red→Green. Each user-facing change ships E2E (FR-044). The six worked memory examples become six unit tests against pure functions. ✔ |
| **VI. Simple, discoverable UX** | **No new surface**: the empty state a panel already returns to becomes the edit screen (FR-007a). Two fields and a checkbox added to a form that already has three. ✔ |
| **VIII. SOLID/DRY/YAGNI** | Extends `resolveLaunchSpec`, the existing poll loop and `updatePanelConfig` rather than adding parallel mechanisms. ✔ |
| **IX. DI & composition root** | The new poll interval and the recipe catalogue are injected, not read ad hoc. ✔ |
| **X. Externalised configuration** | `commandPollMs` is a typed setting with a documented default, not a module constant (FR-019c). ✔ |
| **XI. Panels** | `terminalMemory` lives on the Panel and dies with it (FR-007d). Terminal lifecycle still does not govern Panel lifecycle. ✔ |

**No violations. No complexity deviations to record.**

One constitutional nuance worth stating: Principle III says presets are "executable by the user when a
project opens cold". This feature makes the Panel's own configuration its preset and the Panel's cold
start the execution trigger — automatic rather than a separate user action. That is a *stronger* reading
of the requirement, not a weaker one, and the spec's Overview records it.

## Implementation phases

Ordered so each phase is independently green, and so the highest-risk work is proven early.

**Phase A — the rename and its migration** (FR-002–FR-002f). Touches the most files and nothing depends
on the old names afterwards. Doing it first means every later phase is written in the new vocabulary
once. Read-side migration with fixtures containing the **old** keys.

**Phase B — Startup Command, end to end** (US1, FR-001–FR-014). Recipes, `resolveLaunchSpec`, the form
field, the fallback. Ships US1 alone — the MVP slice.

**Phase C — command observation** (FR-019a–h, FR-022–FR-026). `listChildProcesses`, the contract suite,
the daemon poll, the IPC notification, the renderer store. No persistence yet.

**Phase D — the memory rule** (US2, FR-015–FR-018, FR-025). `captureDecision`, `terminalMemory`,
`clearPanelType` preservation, the pre-filled form, the checkbox. The six worked examples become tests.

**Phase E — directory memory** (US3, FR-027–FR-032). Smallest phase; the observation already exists.

**Phase F — observability** (FR-026a–e). Diagnostics logging plus the conditional toast.

**Phase G — coverage** (FR-042–FR-045). The user-defined-flavour E2E that closes #113, and the E2E for
every user-facing change.

## Risks

| Risk | Mitigation |
|---|---|
| `clearPanelType` erases config at the exact moment memory must persist | Found during planning (research R5). `terminalMemory` is a Panel field it deliberately preserves, with its own test. |
| cmd.exe ignores standard argv quote-escaping | Command occupies a single argv element; a spaces-and-quotes test per built-in (research R1a). |
| The new poll inherits #190's synchronous stall | `listChildProcesses` is **async** by contract; the sync `listChildPids` is untouched. |
| An eager settings rewrite hits the invisible-config-write bug (#102) | Read-side migration — nothing is rewritten until the user next saves. |
| E2E flake baseline | Known pre-existing failures are recorded before any change; the final run is compared against that baseline, not against zero. |
