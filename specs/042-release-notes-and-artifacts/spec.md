# Feature Specification: Release Notes & Multi-Artifact Publication

**Feature Branch**: `feature/S042-I350-I351-release-notes-and-artifacts`

**Created**: 2026-09-02

**Status**: Draft

**Input**: GitHub issues #350 (release notes that say what changed in each release) and #351
(additional installer formats), specified together because they are one pipeline change seen from
two ends: #351 makes a release publish several artifacts, and #350 makes the release body describe
them and what changed.

---

## What this feature is, and what it is not

**A release today tells a reader nothing about itself.** Every published throng release carries an
identical body, generated by a hardcoded string in `.github/workflows/release.yml:249-260`: a
sentence naming the version, the unsigned-installer warning, a one-row SHA-256 table, and the source
commit. Two consecutive releases differ by a version number and a hash. A user asking *"is the
terminal scrolling bug fixed?"* has no answer short of reading the commit log, and a user hitting a
regression cannot tell which release introduced it. There is no `CHANGELOG.md`, so the release body
is the only place that information could live, and it does not live there.

**A release today also ships exactly one artifact, and the pipeline assumes it always will.** That
assumption is not a limitation to be relaxed later — it is a defect waiting for the second artifact,
because it fails *silently*. `release.yml:142` uploads `dist/installer/*.exe`; lines 178, 235 and 246
each independently re-resolve the installer as `ls dist/installer/*.exe | head -n1`, for
verification, for the publish gates, and for the checksum that goes into the release body. Add one
more `.exe`-producing target and those three resolutions can each pick a different file: the gates
would verify one artifact while the release published another's checksum, and nothing in the pipeline
would report it.

**What this feature is not:** it is not a new set of release rules. Spec 020 already governs
publication, and its requirements were written in the plural from the start — FR-042 and FR-042a
require a checksum for **every downloadable artifact**, and FR-024a requires verification to confirm
**each** artifact's recorded checksum against its actual bytes. Those requirements are not
insufficient; the *code* is, and only accidentally satisfies them because there happens to be one
file. This feature makes the pipeline conform to requirements it already has, and adds the artifacts
and the notes on top.

### Requirements this feature supersedes

**One, stated explicitly, per the rule that an older requirement which should change is a
supersession and never a silent contradiction.**

- **020 FR-039**, parenthetical: *"Only one installer per supported platform is needed; there is no
  second Windows installer format in scope."* **Superseded.** A Windows release now publishes three
  artifacts. FR-039's substance — that packaging design must not foreclose macOS or Linux, and that
  platform-specific packaging sits behind the same abstraction discipline — is **unchanged and still
  binding**; only the parenthetical count gives way.

**Nothing else in 020 is superseded, and two requirements are deliberately left standing:**

- **020 FR-040** (per-user install only, never machine-wide) and **020 FR-012** (installation must
  not require administrator elevation) **remain in force for every artifact this feature adds.** An
  earlier draft of this spec proposed a per-machine MSI, which would have superseded both. It was
  dropped: machine-wide installation is a choice that should be offered across *all* installer
  formats if it is offered at all, which is a larger decision than this feature should carry and is
  tracked as **#361**. Consequently **no MSI ships in this feature**, and #351 is only partly
  delivered here — see *Scope* below.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - A release says what changed in it (Priority: P1)

Someone looking at a throng release — deciding whether to take an update, or working out which
release introduced a regression — reads the release body and learns what changed: what was added,
what was fixed, and anything they must now do differently. The installer guidance and the checksums
they already rely on are still there, beneath that content rather than instead of it.

**Why this priority**: This is the headline value of #350 and the reason a release body exists. It
is deliverable over the *current* single-artifact release with nothing else in this feature done, and
it stops being optional the moment v1.0.0 exists and people decide whether to upgrade.

**Independent Test**: Publish two consecutive versions and compare their bodies. They differ by more
than a version number and a hash, and each describes its own changes. Fully testable with one
artifact.

**Acceptance Scenarios**:

1. **Given** a version with merged work behind it, **When** its release publishes, **Then** the
   release body states what changed in that release, grouped so a reader can skim it.
2. **Given** two consecutive published releases, **When** a reader compares their bodies, **Then**
   they differ in content, not only in version number and checksum.
3. **Given** any published release, **When** a reader reaches the bottom of the body, **Then** the
   unrecognised-app warning guidance and the SHA-256 table are both present, unchanged in substance
   from what they say today.
4. **Given** a version whose notes have not been written, **When** publication is attempted,
   **Then** it is refused, the refusal names the missing notes, and no release is created.
5. **Given** a prerelease version (`1.0.0-alpha4`), **When** it publishes, **Then** it carries its
   own notes and is still marked as a GitHub prerelease.

---

### User Story 2 - Every artifact is named, verified and checksummed (Priority: P2)

The pipeline knows exactly which artifacts a release consists of. It verifies each one, computes each
one's checksum from that one's bytes, publishes all of them, and refuses to publish if the set it is
about to publish is not the set that was built and verified.

**Why this priority**: It is the prerequisite for US3 — no format can be added until artifact
resolution is explicit — and it is independently valuable before that, because it converts 020's
FR-024a and FR-042a from accidentally-true into enforced. It is also what makes US1's checksum table
correct by construction rather than by there happening to be one file.

**Independent Test**: With today's single artifact, confirm the pipeline names it explicitly rather
than globbing, and that removing or renaming an expected artifact fails the run with a message naming
which artifact was missing.

**Acceptance Scenarios**:

1. **Given** a packaging run, **When** it completes, **Then** the pipeline holds a declared set of
   artifacts, each identified by role and filename, rather than discovering them with a wildcard.
2. **Given** the declared set, **When** verification runs, **Then** every artifact in the set is
   verified, and a set member that was not verified fails the run.
3. **Given** the declared set, **When** publication runs, **Then** each artifact's checksum is
   computed from that artifact's own bytes and appears in the release body against that artifact's
   own filename.
4. **Given** a build that produced a different set of artifacts from the one declared, **When**
   publication is attempted, **Then** it is refused and the refusal names the discrepancy.
5. **Given** two artifacts sharing a file extension, **When** any pipeline step resolves an artifact,
   **Then** it resolves the one it means, and no step's choice depends on filesystem ordering.

---

### User Story 3 - throng without an installer (Priority: P3)

Someone who cannot or will not run an installer — a locked-down machine, a USB stick, or simply
trying throng out without committing to an install — downloads a portable build, runs it from a
folder, and gets a working throng with working terminals. Nothing is installed, and removing the
folder removes throng.

**Why this priority**: A real audience with no route in today, but one that depends on US2 landing
first and delivers nothing without it. Lower than US1 because a release nobody can read is a worse
problem than a release one audience cannot install from.

**Independent Test**: On a clean machine, extract the archive and run throng from the extracted
folder. Create a project, spawn a terminal, close it, delete the folder. Nothing installed, nothing
left behind.

**Acceptance Scenarios**:

1. **Given** a published release, **When** a user downloads the portable artifact, **Then** running
   it starts throng without any installation step and without administrator rights.
2. **Given** a published release, **When** a user extracts the archive artifact to a folder and runs
   throng from it, **Then** the application starts, spawns its daemon from the bundled runtime, and
   opens a working terminal.
3. **Given** a portable or archive run, **When** the user closes throng and deletes the folder,
   **Then** no throng process is left running and no component of the application remains in that
   folder's place.
4. **Given** the release body, **When** a reader looks at the artifact list, **Then** it tells them
   which artifact they want and why.

### Edge Cases

- **A version is tagged with no notes written for it.** Publication must be refused, naming the
  missing notes. It must not fall back to the old boilerplate — a fallback that produces a plausible
  body is how an unreviewed release ships.
- **Notes exist but describe a different version.** Must be refused the way 020 FR-030 refuses a
  sign-off bound to a different build; notes for `1.0.0` must not publish `1.0.1`.
- **A release with nothing user-visible in it** (a CI-only or docs-only version). The notes must be
  able to say so honestly rather than being padded or left empty — an empty section and a missing
  section are different states, and only the second one fails publication.
- **Two artifacts share an extension.** The portable build and the setup wizard are both `.exe`.
  Every resolution must name which it wants; this is the concrete failure US2 exists to prevent.
- **An artifact is built but not verified, or verified but not published.** Either direction is a
  gate failure: the published set and the verified set must be the same set.
- **A verification harness that only knows how to drive an installer.** A portable artifact has no
  install step and no uninstaller, so "installs cleanly / uninstalls cleanly" has no meaning for it.
  Each format needs a verification path appropriate to it that still proves the same end state — the
  app launches, the daemon runs from the bundled runtime, a terminal works, and nothing is left
  behind afterwards.
- **A new target that repacks the application.** throng is deliberately not asar-packed, ships its
  workspace `packages/*` structure verbatim, maps each library into a real `node_modules/@throng/*`,
  and bundles a pinned host-Node runtime under `resources/runtime` that spawns the daemon as a
  separate non-Electron process with host-ABI native modules (020 FR-009). A target that flattens,
  repacks or rebuilds any of that produces an artifact that starts and then fails — invisibly to a
  smoke test, which is why verification exists.
- **The release body grows past what GitHub will accept.** A body has a size limit; a release with a
  very large set of changes must still publish, with the notes truncated or linked rather than the
  publication failing.

## Requirements *(mandatory)*

### Functional Requirements — release notes

- **FR-001**: A published release body MUST state what changed in that release. It MUST distinguish
  at least what was added, what was fixed, and anything a user must do differently, grouped so a
  reader can skim it.
- **FR-002**: The content of a release's notes MUST be derived from the work between the previous
  release and the one being published, by a rule that is defined and documented. It MUST NOT be
  composed freehand at publication time.
- **FR-003**: A release's notes MUST exist as a reviewable artifact in the repository **before** the
  release is tagged, so that reviewing them is reviewing a diff rather than approving text nobody has
  read.
- **FR-004**: A person MUST be able to correct a release's notes before publication, and MUST NOT
  have to perform any manual step during publication to do so. *(020 FR-036: once the gates are
  satisfied, publication requires no manual step.)*
- **FR-005**: Publication MUST be refused, with no override path, when a release's notes are absent,
  empty, or bound to a different version than the one being published. The refusal MUST name which of
  those it is. *(020 FR-031: a refusal states which condition was unmet. 020 FR-037: gates are not
  bypassable.)*
- **FR-006**: The complete release body that publication will use MUST be rendered and made
  inspectable **before** the gated publication step runs, so the person giving the QA sign-off is
  approving the text that will actually be published.
- **FR-007**: Every release body MUST continue to carry, beneath the notes content: the
  unrecognised-app warning and how to proceed past it, how to verify a download against its checksum,
  the SHA-256 table, and the exact source revision the artifacts were built from. This content is
  load-bearing — `docs/installation.md` tells users the notes list the checksum, and 020 FR-043 makes
  the notes responsible for explaining the warning — and MUST NOT be displaced by the new content.
- **FR-008**: A SemVer prerelease version and a full release version MUST take the same path and both
  MUST produce a valid body. A prerelease MUST still publish as a GitHub prerelease.
- **FR-009**: A release with no user-visible change MUST be publishable, with notes that say so. An
  empty notes section and a missing notes section are different states: only the missing one fails
  FR-005.
- **FR-010**: If a release body would exceed the size the publishing platform accepts, publication
  MUST still succeed, with the notes reduced or linked rather than the release refused.

### Functional Requirements — the artifact set

- **FR-011**: A release MUST have a **declared artifact set**: an explicit list of the artifacts that
  release consists of, each with a stable role and its filename. The set MUST be declared in one
  place and MUST be the single source every pipeline step resolves against.
- **FR-012**: No pipeline step may resolve an artifact by wildcard, by file extension alone, or by
  filesystem ordering. Every step that reads, verifies, checksums, uploads or publishes an artifact
  MUST name which artifact of the declared set it means.
- **FR-013**: Packaging MUST fail when the artifacts actually produced do not match the declared set
  — an artifact missing, an artifact present that was not declared, or a filename that does not match
  what was declared. The failure MUST name the discrepancy.
- **FR-014**: **Every** artifact in the declared set MUST be verified before publication, to the same
  end state the current installer verification proves: the application launches, reports the expected
  version, spawns its daemon from the bundled runtime, opens a working terminal, and leaves no
  process or component behind when removed. *(020 FR-024a already requires this per artifact.)*
- **FR-015**: A verification path MUST be appropriate to its artifact's format. A format with no
  install step MUST NOT be verified by asserting an install step succeeded; it MUST be verified
  against the same end state by whatever route that format offers.
- **FR-016**: Publication MUST be refused when the set it is about to publish is not the set that was
  built and verified. The refusal MUST name which artifact is unverified or unexpected.
- **FR-017**: Every artifact in the declared set MUST be attached to the published release, and each
  artifact's SHA-256 MUST appear in the release body against that artifact's own filename. Each
  checksum MUST be computed from that artifact's exact published bytes, as the last step that reads
  them. *(020 FR-042, FR-042a.)*

### Functional Requirements — the artifacts themselves

- **FR-018**: A release MUST publish, in addition to the existing per-user setup installer, a
  **portable** artifact that runs throng without any installation step, and an **archive** artifact
  that runs throng from an extracted folder.
- **FR-019**: Every artifact this feature adds MUST install or run **without administrator
  elevation** and MUST NOT install machine-wide. *(020 FR-012 and 020 FR-040, both left standing —
  see* Requirements this feature supersedes *above.)*
- **FR-020**: Every artifact this feature adds MUST preserve the packaging layout the application
  depends on: not asar-packed, the workspace package structure shipped verbatim, each library mapped
  into a real package path, and the pinned host-Node runtime bundled so the daemon runs as a separate
  non-Electron process with host-ABI native modules. *(020 FR-009.)*
- **FR-021**: Running throng from a portable or archive artifact and then removing its folder MUST
  leave no throng process running and no application component behind in that location.
- **FR-022**: Per-user data — projects, sub-workspaces, layouts, window state, settings, keybindings,
  custom themes, the edit list — MUST behave consistently across artifact formats, and a user who
  moves between formats MUST NOT silently acquire a second, separate set of it.

### Functional Requirements — documentation

- **FR-023**: `docs/installation.md` MUST tell a reader which artifact to choose and why, and MUST
  keep its existing statement that the release notes carry the checksum true.
- **FR-024**: `docs/releasing.md` MUST document the artifact set the pipeline produces, where release
  notes come from, who reviews them and when, and exactly what fails a release.

### Key Entities

- **Artifact set**: the declared list of artifacts a release consists of. Each member has a role
  (setup installer, portable, archive), a filename, and — once built — a checksum over its own bytes.
  It is declared once and consumed by packaging, verification, the publish gates and the release body.
- **Release notes**: the human-readable account of what changed between the previous release and this
  one, existing as a reviewable repository artifact before the tag, and bound to exactly one version.
- **Release body**: what is actually published — the release notes, then the fixed footer (warning
  guidance, checksum verification instructions, the per-artifact SHA-256 table, the source revision).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A reader comparing any two consecutive published releases can state at least one
  specific change between them, using only the release bodies, in under 60 seconds.
- **SC-002**: A user who hit a defect can determine which published release fixed it from the release
  bodies alone, without reading the commit log or the issue tracker.
- **SC-003**: 100% of published artifacts carry a correct checksum against their own filename in the
  release body — verified by re-computing every published artifact's digest and comparing.
- **SC-004**: A release whose notes are missing, empty-by-omission, or bound to another version is
  refused 100% of the time, with a refusal naming the cause, across every attempted route to
  publication.
- **SC-005**: A person with no development tools on a clean Windows 11 machine can go from downloading
  the portable artifact to a running throng with a live terminal in under 3 minutes, without an
  administrator password and without installing any prerequisite. *(The same bar 020 SC-001 sets for
  the installer.)*
- **SC-006**: Removing a portable or archive throng leaves zero throng processes running and zero
  application components in place, confirmed by a residue scan.
- **SC-007**: No pipeline step resolves an artifact ambiguously — demonstrated by adding a second
  artifact sharing an extension and confirming every step still resolves the artifact it means.

## Assumptions

- **Release notes are compiled at release-preparation time and committed before the tag, and the
  pipeline reads only what was committed.** This is the decision FR-002 and FR-003 leave to design,
  recorded here as the assumption the rest of the spec is written against. It was chosen over the two
  alternatives the issue named. Deriving notes at publication time from **closed issues** was
  rejected because an issue closes for many reasons and a milestone is not a release, so the set of
  issues closed between two tags is not the set of changes in that release. Deriving them from **PR
  titles** was rejected because a PR title summarises a change for a reviewer, not for a user. A
  committed artifact also puts the review where a review already happens — on a diff, before the tag
  — rather than inventing a new approval step, which is what FR-004 and 020 FR-036 require.
- **The existing GitHub Environment approval remains the QA sign-off**, unchanged in meaning. This
  feature adds the rendered body to what that approver can see (FR-006); it does not add a second
  approval, and 020 FR-029's rule that the sign-off is an irreducibly human act is untouched.
- **The three artifacts are built by the existing packaging tool** from the same application build.
  Nothing in this feature rebuilds the application per format.
- **Windows only.** 020 FR-038 makes Windows 11 the only packaged platform, and FR-039's requirement
  that packaging not foreclose other platforms is unchanged by this feature.
- **`npm run verify:installer` is extended rather than replaced.** It already encodes the end state
  that matters (launch, version, daemon, terminal, uninstall, residue); what varies per format is how
  the artifact is put on disk and taken off again.

## Scope

**In scope**: everything in #350; the artifact-set, verification and checksum half of #351; the
portable and archive artifacts; the two documentation requirements above.

**Out of scope, and why**:

- **An MSI, and machine-wide installation generally.** Dropped from this feature by the maintainer's
  decision that machine-wide install should be a choice offered across *all* installer formats rather
  than a property of one of them. That is a supersession of 020 FR-040 and FR-012 and a doubled
  install/upgrade matrix, and it needs its own specification — tracked as **#361**. **#351 is
  therefore only partly delivered by this feature** — its MSI acceptance criteria move to #361.
- **Code signing** (#118) and the unsigned-app warning wording it owns. 020 FR-042/FR-043 stand.
- **Automatic update** (#119). This feature is about the published text and files, not delivery.
- **macOS** (#22) and **Linux** (#23) packaging.
- **Microsoft Store / MSIX**, and the `appx` and `msi-wrapped` targets — no named audience.
- **Any channel other than the GitHub Release body.**

## Dependencies

- **Spec 020 (Application Packaging)** — the governing spec. This feature supersedes exactly one
  parenthetical in its FR-039 and conforms the pipeline to its FR-024a, FR-036, FR-037, FR-042 and
  FR-042a.
- **Issue #350** — release notes. Delivered in full.
- **Issue #351** — additional installer formats. Delivered in part; the MSI half is deferred to #361.
- **Issue #361** — machine-wide installation as a choice across every installer format. Supersedes
  020 FR-040 and FR-012, which this feature deliberately leaves standing. Blocks #351's MSI half.
- **Issue #118** (code signing) — will change the release body's warning footer and will apply its
  own gate to every artifact in the declared set. The two must agree on how many artifacts a release
  has, which is what FR-011 gives it.
- **Issue #119** (automatic update) — update behaviour differs by artifact format, and a portable
  build has none.
